# ch-adclick · 广告点击事件聚合

定位：大型广告平台的点击流实时聚合。聚合结果直接用于计费，所以这是一道"正确性优先"的流处理题。

## Step 1 · 需求澄清

- 聚合结果用来干什么？计费 → 正确性压倒一切，延迟可放宽到分钟级。
- 支持哪些查询？某广告最近 M 分钟点击数 / 每分钟 top 100 / 按维度过滤。
- 迟到和重复事件要处理吗？必须 → event time + watermark + 日终对账。
- 原始数据要留吗？原始和聚合都存。

## Step 2 · 规模与需求

- Scale：10 亿点击/天，200 万广告，年增 30%；均值 1 万 QPS，峰值 ×5 = 5 万 QPS；0.1KB/事件 → 日增约 100 GB。
- FR：① 某 ad 最近 M 分钟点击数 ② 每分钟 top 100 广告 ③ 按 ip / user_id / country 过滤。
- NFR：正确性优先，端到端延迟几分钟可接受；迟到、重复、组件故障都要处理。

### 存储选型

| 组件 | 选型 | 为什么 | 没选什么 |
|---|---|---|---|
| Kafka #1 原始点击 | Kafka | 高吞吐追加，聚合服务要能回放；按 ad_id 分区，同广告有序 | 普通消息队列：消费即删，不能回放 |
| Kafka #2 聚合结果 | Kafka | "发结果 / 存 offset / 收 ack"要放进同一个事务，靠 Kafka 事务写 + offset 原子提交；下游 DB 挂了结果留在这里不丢 | 聚合服务直接写 DB：写库和 offset 提交无法原子，重放就重复计数 |
| 原始库 | Cassandra | 写重（峰值 5 万 QPS），按 (ad_id, 小时桶) + 时间范围读 | S3 + Parquet：适合冷数据批量扫描 |
| 聚合库 | Cassandra | 只按 ad_id + click_minute (+ filter_id) 查最近 M 分钟，同一分区内按分钟聚簇的范围读；和原始库同栈 | 关系库：写入量随广告数 × 分钟线性涨，分库分表成本高，且不需要跨行事务 |

### 关键设计决策

- 原始和聚合都存：原始是事实源（可重算、可 debug），聚合是查询面（小、快）。
- 聚合表键 = (ad_id, click_minute) (+ filter_id)；过滤维度用预定义 filter_id 做 star schema 预聚合。
- 双 Kafka 夹一个聚合服务：下游 Kafka 是端到端 exactly-once 的关键。
- 聚合服务是 MapReduce DAG：Map（清洗、按 ad_id 分流）→ Aggregate（每分钟内存计数，top-N 用堆）→ Reduce（局部 top-N 合并成全局）。
- 架构选 Kappa，不选 Lambda：只有一套聚合代码。历史重算 = 新起专属聚合实例，以原始库为输入重跑同一套聚合代码，结果写 Kafka #2，覆盖聚合库里对应的 (ad_id, 分钟)。

## Step 4 · 深挖

### 时间语义

| 选项 | 时间戳来源 | 问题 |
|---|---|---|
| Processing time | 聚合服务器的系统时间 | 事件迟到就被算进错误的窗口，计费失真 |
| Event time ✓ | 客户端点击时刻 | 客户端时钟可能不准；必须处理迟到 |

### watermark

- 聚合窗口：1 分钟 tumbling window 做每分钟计数；3 分钟、每分钟滑一次的窗口做"最近 M 分钟 top N"。
- watermark：给每个 1 分钟窗口尾部多等一段可调时长（示例 15 秒），让稍晚到的事件还能进窗。等得长 → 更准但延迟高；等得短 → 反之。
- 谁推进 watermark：聚合服务按自己读到的事件时间戳推进，watermark = 已读到的最大 event time − 允许的乱序量（15 秒）。
- 救不了迟到很久的事件，残余误差交给日终对账。

### 积压时会算错吗

- 不会，只会晚出。窗口按事件时间划分，关窗看 watermark，不看墙上时钟。
- 消费慢 → 读到的时间戳慢 → watermark 慢 → 窗口晚关。
- 积压的事件留在 Kafka #1（offset 未提交），不丢；lag 超过 Kafka 保留期才是真丢。
- 算力决定延迟，不决定正确性：平均消费速率 ≥ 平均写入速率即可，峰值由 Kafka 缓冲。

### Exactly-once

- 重复来源：客户端重发、聚合节点故障。
- 典型时序：聚合节点消费 offset 100→110，结果已发下游，但向上游提交 offset=110 失败 → 接手节点从 100 重读 → 重复计数。
- 先存 offset 再发结果 → 发送失败就丢数据；收到 ack 再存 offset → 存之前挂了又重复。
- 解法："发结果、存 offset、收 ack"放进一个分布式事务（Kafka #2 + 原子提交）。

### 热点广告

- 按 ad_id 分区，大广告主的点击集中到少数节点。过载节点申请临时节点分担，结果合并回原节点。

### 故障恢复

- 聚合状态在内存：定期快照（上游 offset + 最近 M 分钟中间态），新节点从快照恢复，之后的增量从 Kafka 补。

### 对账

- 聚合结果没有第三方可核对，只能自己对自己：日终批任务把每个 partition 的事件按 event time 重排、重新聚合，和实时结果比对。
- 批算和流算都对，也可能因迟到事件有小偏差，属预期。

## 易错点

- 把延迟要求当成竞价的亚秒级：这里是计费报表，几分钟即可。
- 只说 at-least-once + 去重：要能画出 offset 提交失败的时序。
- 把 watermark 当银弹：它只救稍微迟到的事件。
- 监控看"队列长度"：Kafka 是 commit log，要看 consumer lag。
